Every drop makes the drone lighter.

So the order it flies its stops in changes what every later leg costs.

This project models drone delivery with energy that depends on the weight still onboard, under battery, payload, fleet-size and no-fly limits. It solves the problem exactly where that is possible, with three metaheuristics where it isn't, and checks the answers against brute force and against 74 published optima.

e(d, w) = d · (α + βw)
d
leg length, km
w
payload still onboard, kg
α = 1
the airframe's own share
β = 0.3
a full load costs ~30% more per km

Fly the same stops in a different order and the bill changes.

In ordinary vehicle routing, a loop flown backwards costs the same. Here it doesn't. A drone lifts every parcel at the depot and sheds weight at each stop, so a heavy parcel dropped early makes every leg after it cheaper. The shortest route and the cheapest route can be different routes.

Five solvers, one objective.

All five share one implementation of the energy function and one feasibility check, so a comparison between them is fair by construction. Greedy warm-starts the rest. Branch & Bound proves optimality on small instances; the metaheuristics carry on where it runs out of time.

No metaheuristic has ever returned a value below a proven optimum. If one did, the objective or the exact method would be wrong, which makes it the project's main internal correctness check.

The Split decoder

The GA, SA and ALNS never see routes. They see one ordering of all twenty customers, with no route boundaries. A dynamic program then decides where to cut it into at most five feasible routes so that total energy is lowest.

Crossover and mutation only ever rearrange a permutation, so they can't produce an invalid solution. Every feasibility question is answered inside Split, and a test enumerates every possible segmentation to prove Split finds the best one.

The plan above, as the metaheuristics store it. Split cuts it back into exactly these five routes.
state (i, k) = first i customers covered with exactly k routes
answer = min over k ≤ K of dp[n][k], so the fleet limit is exact, never a penalty

What has been checked, and what hasn't.

Every number in the study lives in a SQLite store, one row per run, tagged with the git commit that produced it. The report's tables are generated from it. Findings that didn't survive re-measurement were retracted in the log, not quietly dropped.

Exact method

A timed-out search still says how good its answer is.

$ drp solve city.json --method bnb --time 5
  energy   : 1504.69
  status   : timed out -- lower bound 288.40, gap 80.83%

Branch & Bound keeps every unexplored sibling on a frontier, so the minimum over it is a valid global lower bound even at a 1 ms cut-off. It proves optimality for n = 5 to 9 in the committed run. The bound is weak, and the log says so: from n = 15 its value is still the greedy warm start.

Ablation · 528 runs

Simulated annealing's reheats were hurting it.

Removing one component at a time across 11 instances and 3 seeds: SA without reheats improves on 10 of 11 instances and halves its mean gap, p = 0.002. It is the only one of thirteen comparisons that survives a Bonferroni correction, so the rest are reported as leads, not results.

The same study found the GA genuinely needs its constructed start: without it, it finishes 2.75 points worse.

From a recipe to a flight plan.

One command-line tool, drp, covers the whole path: build an instance from a scenario, solve it, look at it, and export it to the ground-control software a real drone flies from. Every HTML view is a single self-contained file.

Install the package and the drp command.

pip install -e ".[dev]"

Generate a city: 20 stops, 5 drones, 3 polygonal no-fly zones.

drp generate --n 20 --drones 5 --zones 3 --seed 7 -o city.json

Or build one from real Pontianak coordinates and a written recipe.

drp build scenario.json -o geo.json

Solve it. Swap in bnb, ga, sa or greedy.

drp solve geo.json --method alns --time 10 -o sol.json

Replay the flight in a browser, or open the B&B tree and convergence views.

drp show sol.json --instance geo.json --web flight.html

Skip the JSON: place stops on a map in a local planner.

drp serve

Export one QGroundControl mission per drone.

drp export sol.json --instance geo.json --format qgc -o missions/
missions/
